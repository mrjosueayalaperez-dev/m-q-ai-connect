## 4. Part C — Shared intelligence layer: feasibility notes

**What CONNECT already defines that a shared, permission-controlled knowledge layer can reuse (all VERIFIED as documents/governance):**
1. **The architecture decision itself**: shared layer = library + registry + workflow patterns, *not* a central runtime; projects call in; the layer never pulls project data; no monolithic cross-project model. A shared *knowledge* layer fits this exactly if it is built as versioned, scope-tagged assets (approved curriculum corpus, method prompts, glossaries) that each app consumes inside its own boundary — and violates it if built as one shared database of student/trading data.
2. **The Capability Registry discipline**: owner + approved consumers + evidence + last-verification date per capability; maturity ladder; scope-widening = new founder decision. An "AI Professor grounding pack" or "strategy explanation pack" would enter as registry entries, not as shared code by default.
3. **The Integration Registry pattern**: every connection documents what is shared, what is explicitly NOT shared, and its verification evidence — the exact paperwork a cross-app knowledge flow needs.
4. **Hard boundaries already legislated**: private user information never crosses projects; the three bridges are absolutely separate; CONNECT has no autonomous powers (no spending, no DB access, no trade execution). Any shared layer inherits these as constraints, not options.
5. **A working code-level precedent**: the Copilot's `ProviderRegistry` (VERIFIED) already implements "one dispatch, many providers, common signature" — the shape a shared model-access layer would take. It currently lives inside the Dashboard repo with one consumer; extracting/generalizing it is a design decision, not a discovery problem.
6. **Eval discipline on file**: Quality Center's 33 deterministic cases + dual-record rule (deterministic results and founder verdicts preserved side by side) and the Copilot's own test patterns (refusal-without-provider-call, disclaimer-always, no-key-material-in-responses) are the acceptance-test vocabulary a shared layer's consumers can reuse (PROPOSED reuse; Quality Center itself is research-only, repo not created).

**What does not exist yet (the honest gaps):**
- No shared runtime, API, or service of any kind connects the two apps. The University has no backend at all; the Dashboard backend is not deployed on its target host. A shared layer today would be **shared files/assets + governance**, not shared infrastructure.
- No vector store / embeddings pipeline exists in either app or in CONNECT. The Supabase project's pgvector status is UNKNOWN.
- No cross-app identity or permission system: Dashboard has per-user JWT auth; University has no accounts. "Permission-controlled" across both currently means: Dashboard-side auth (exists) + University-side nothing-to-control (no accounts, no server data).
- No shared knowledge asset has been packaged yet: the two apps' strategy content is *parallel* (University lessons l8/l9; Copilot method prompts; `docs/strategies/STRATEGY_A_SIX_GATES.md` in the Dashboard repo) — three renderings of the same doctrine, maintained separately, with no single source-of-truth file designated. (Drift risk is real but unmeasured: UNKNOWN whether the three renderings currently agree in every detail.)
- Langfuse (the natural observability seat for a shared layer) is an empty Hobby account; its POC is assigned and unrun; the standing rule from the POC brief — **no Copilot connection** to Langfuse — currently forbids the most obvious integration.
